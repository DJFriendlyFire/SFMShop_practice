# Ответы на вопросы о тестировании

## Какой у тебя подход к тестированию?
Использую модульное тестирование для проверки критической бизнес логики.
В проекте написал тесты для всех критических функций и классов.
Использую pytest для написания тестов, фикстуры для подготовки данных и параметризацию для проверки разных случаев.
Так же применяю TDD для новых функций - сначала пишу тесты, потом реализую код.
Для изоляции тестов от внешних зависимостей использую моки через unittest.mock

## Какие типы тестов ты пишешь?
Пишу unit тесты для проверки отдельных функций и классов. Например в проекте я написал тесты для функций расчетов скидок и
расчетов стоимости доставки, так же для классов Order, Product, User.
Так же пишу интеграционные тесты для проверки взаимодействия между компонентами. Например тесты API endpoints с
мокированием БД.

## Какое покрытие кода?
Достиг покрытия 80% для критичной бизнес логики. Использую pytest-cov для проверки покрытия.
Важно не гнаться за покрытием в 100%, а покрывать тестами критичные части: бизнес логика, функции расчета, обработку ошибок.

## Как ты используешь моки?
Использую моки для изоляции тестов от внешних зависимостей. В проекте замокировал БД через unittest.mock.patch для тестов
API endpoints, чтобы тесты были быстрыми и не зависели от реальной БД.

## Что такое TDD?
Test Driven Development - это подход при котором сначала пишутся тесты, а потом реализуется код.
Использую цикл красный-зеленый-рефакторинг. Сначала пишу тест, затем минимальный код для прохождения теста, после 
улучшаю код сохраняя прохождение тестов.
В проекте использовал TDD для функции расчета доставки.




# Подход к тестированию в проекте SFMShop

## Обзор

Проект SFMShop — это REST API для электронной коммерции, построенное на **FastAPI** с использованием **PostgreSQL** и **RabbitMQ**. 

Подход к тестированию основан на следующих принципах:
- **Автоматизация** — все критические компоненты покрыты автоматическими тестами
- **Изоляция** — тесты не зависят от внешних сервисов (БД, RabbitMQ) благодаря мокам
- **Скорость** — тесты выполняются быстро за счет использования моков и фикстур
- **Пирамида тестирования** — баланс между unit, интеграционными и API тестами

Для запуска тестов используется **pytest** с плагинами **pytest-asyncio** (для асинхронных тестов) и **pytest-mock** (для мокирования).

## Типы тестов

В проекте реализованы следующие типы тестов:

### 1. Unit-тесты (`tests/test_models.py`, `tests/test_utils.py`)
Проверяют отдельные функции и модели:
- **Модели Pydantic** — `UserResponse`, `ProductResponse`, `OrderResponse` (валидация данных, сериализация)
- **Функции бизнес-логики** — `calculate_delivery()` (расчет стоимости доставки)
- **Параметризованные тесты** — проверка функции на разных наборах данных

Пример:
```python
@pytest.mark.parametrize("weight,distance,expected", [
    (1, 10, 160),
    (5, 50, 400),
    (10, 100, 700),
])
def test_calculate_delivery(weight, distance, expected):
    assert calculate_delivery(weight, distance) == expected
```

### 2. API-тесты (`tests/test_api.py`)
Интеграционные тесты для проверки HTTP endpoints:
- **GET /api/v1/products** — получение списка товаров
- **POST /api/v1/orders** — создание заказа
- **Аутентификация** — тестирование с подменой JWT-зависимости

Особенности:
- Используется `TestClient` для эмуляции HTTP-запросов
- Зависимости (БД, аутентификация) подменяются через `app.dependency_overrides`
- Асинхронные функции мокируются через `AsyncMock`

### 3. Интеграционные тесты (планируются)
Для тестирования с реальной БД и RabbitMQ:
- Тесты миграций базы данных
- Тесты consumer/producer очередей
- End-to-end сценарии создания заказа

## Покрытие кода

**Целевое покрытие:** 80% для критической бизнес-логики

**Инструменты:**
- `pytest-cov` — сбор метрик покрытия
- Отчеты в HTML (`htmlcov/`)

**Приоритеты покрытия:**

| Компонент | Приоритет | Статус |

|-----------|-----------|--------|

| Модели (User, Product, Order) | Высокий | ✅ Покрыто |

| API endpoints (CRUD) | Высокий | ✅ Частично |

| Функции расчетов (delivery, discount) | Высокий | ✅ Покрыто |

| Database queries | Средний | ⏳ В планах |

| RabbitMQ producer/consumer | Средний | ⏳ В планах |

| Middleware (logging, auth) | Средний | ⏳ В планах |


**Команда для запуска с покрытием:**
```bash
pytest --cov=src --cov-report=html
```

## Организация тестов

```
tests/
├── __init__.py              # Пакет тестов
├── test_models.py           # Unit-тесты моделей Pydantic
├── test_utils.py            # Unit-тесты утилитных функций
├── test_api.py              # API-тесты endpoints
└── conftest.py              # Общие фикстуры (планируется)
```

**Структура тестов:**
- **Фикстуры** — переиспользуемые данные (`sample_product`, `sample_user`, `sample_order`)
- **Моки** — изоляция от внешних зависимостей (`mock_get_db_pool`, `mock_get_current_user`)
- **Параметризация** — тестирование разных сценариев через `@pytest.mark.parametrize`

**Запуск тестов:**
```bash
# Все тесты
pytest

# С выводом покрытия
pytest --cov=src

# Конкретный файл
pytest tests/test_api.py -v

# С выводом логов
pytest -s
```

## Использованные техники

### 1. Фикстуры pytest
```python
@pytest.fixture
def sample_product():
    """Фикстура: тестовый товар"""
    return ProductResponse(id=1, name="Тестовый товар", ...)
```

### 2. Мокирование зависимостей FastAPI
```python
app.dependency_overrides[auth.get_current_user] = lambda: mock_user
app.dependency_overrides[get_db_pool] = lambda: mock_pool
```

### 3. AsyncMock для асинхронных функций
```python
mock_create_order = mocker.patch(
    "src.api.routes.orders.order_queries.create_order_with_conn",
    new_callable=AsyncMock
)
```

### 4. Параметризация тестов
```python
@pytest.mark.parametrize("weight,distance,expected", [...])
def test_calculate_delivery(weight, distance, expected):
    ...
```

### 5. TestClient для HTTP-тестов
```python
client = TestClient(app)
response = client.get("/api/v1/products?skip=0&limit=2")
```

### 6. Автосброс зависимостей
```python
@pytest.fixture(autouse=True)
def reset_dependencies():
    yield
    app.dependency_overrides.clear()
```
